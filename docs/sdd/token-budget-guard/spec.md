# Spec — token budget guard: a skill version that adds session tokens never reaches users

## Problem

Owner rules (12/Nov/2026):

- "ทุกครั้งที่มีการอัปเดตสกิล ต้องคำนึงถึงการกิน token สุทธิต่อรอบ session นึง ให้น้อยที่สุดเสมอ"
- "สร้างแนวกันพลาด 10 ชั้น ถ้าไม่ได้ตามกฎที่เราสั่ง ห้ามเอาเวอร์ชันนั้นขึ้น prod"

In this spec, "prod" for helix is a published release tag `vX.Y.Z`. Users' installs move only to the newest release tag (`scripts/helix-auto-update.sh:107`), and the `publish` job creates that tag on every push to `main` (`.github/workflows/version.yml:70`). Today nothing measures tokens anywhere on that path. The token-diet numbers come from a script in ols-qa-evidence (`graph_v2.py`) that someone has to remember to run. `main` has no branch protection (GitHub API returns 404).

## Definitions

- **Session cost** of a skill: the always-on description bytes of all skills, plus that skill's mandatory-read tokens (bytes/4, graph_v2 method), direct and via the helix router. This follows the token-diet G1 definition.
- **Budget**: `token-budget.json` at the repo root. It records, per skill, the direct and routed mandatory tokens, plus the total always-on description bytes, all measured on the last release. It is the only baseline.

## Rules

- **R1 (budget file).** The repo must carry `token-budget.json`, generated by `scripts/token-measure.py` from a release commit and listing the commit it was measured on. **Baseline provenance (12/Nov/2026, after helix#38):** `scripts/check-budget-baseline.sh` must find the commit that first wrote the budget's current `tag` + `commit` (the ratchet or generate commit). That copy must equal a fresh `token-measure.py` measurement of `commit` exactly. Every later non-merge commit that changes the file may only lower or keep the numbers, unless its commit message contains `[token-budget-raise]` (the R9 path, whose PR title and owner quote the `token-budget-raise` job checks). An uncommitted raise in the work tree fails. So the current budget may sit above the named release's measurement only through recorded R9 raises, never silently.
- **R2 (measurement).** `scripts/token-measure.py` must compute session cost the same way graph_v2.py does. Its known-answer self-test must reproduce the token-diet numbers for helix `18200e2` exactly. If the self-test fails, the check fails.
- **R3 (pre-commit).** When staged files touch `skills/`, `references/`, `commands/` or `hooks/`, the pre-commit hook must measure the staged tree. It must refuse the commit if any skill's direct or routed cost, or the always-on total, is higher than the budget.
- **R4 (pre-push).** The pre-push hook must run the same check on the pushed head. This catches a commit made with `--no-verify`.
- **R5 (PR check).** CI must run a `token-budget` job on every PR. The job compares the PR head with the budget and fails on any increase. It also posts the per-skill before → after table in the job summary.
- **R6 (required check).** Branch protection on `main` must require `token-budget` and `pr-check` to pass before a merge. This is a GitHub setting that needs the owner's approval.
- **R7 (release gate).** The `publish` job must re-measure the exact commit it is about to tag. If the cost is above the budget, or if R8's rule-line check fails, it must not create a tag or release.
- **R8 (no gate dropped to save tokens).** The PR and release checks must diff the rule lines (MUST / NEVER / 🔴 / STOP / GATE) between base and head. A removed rule line fails the check unless the same line exists elsewhere in the tree, i.e. it was moved, not cut (global rule 7). **Reword register (owner 12/Nov/2026):** a removed line also passes when `rule-line-register.json` lists it with an owner approval and one or more replacement lines that each carry a rule keyword and exist in the head tree. Adding register entries needs a PR titled `[rule-reword]` whose body quotes the owner (same pattern as R9).
- **R9 (raising the budget).** `token-budget.json` may only go up in a PR whose title starts with `[token-budget-raise]` and whose body quotes the owner's approval. A separate CI job checks both, and CODEOWNERS assigns the file to the owner. Any other change to the file must lower the numbers or keep them the same. A decrease is written automatically after each release, so the bar only ratchets down.
- **R10 (user-side check).** Every release must attach `token-report.json`: the measured costs, the budget, the commit and the verdict. `helix-auto-update.sh` must refuse to move an install to a release whose report is missing or whose verdict is not `pass`. In that case it stays on the current version and prints one line saying why. This change touches every user, so it needs the owner's approval.

## Out of scope

- The ols-qa repository. It has its own release and sync. Mirroring R3–R5 there is a separate follow-up.
- Output-side tokens of a run (no measurement method yet).

## Edge cases

- A skill that is new has no budget entry. Its first PR must be a `[token-budget-raise]` PR (R9).
- A change that only lowers the cost passes, and the next release writes the lower numbers into the budget.
- After an approved raise (R9) the budget names the same release but holds higher numbers. R1 passes: the release's own copy still equals its measurement, and the raise is a `[token-budget-raise]` commit. A raise hidden in a merge commit's conflict resolution is not seen by R1 (it reads non-merge commits); the R5 `token-budget` and R9 `token-budget-raise` PR jobs still diff the whole PR.
- If the measurement itself fails (missing file, parse error), every layer must treat it as a fail, never a pass.

## Done when

- Each of R1–R10 has a test in `scripts/tests/` that fails before its change and passes after it.
- A PR that adds 1 token to any skill's mandatory reads fails layers R3, R4, R5 and R7 in a dry run, and its release is not created.
- A release whose `token-report.json` verdict is `fail` is refused by `helix-auto-update.sh` in the update test.
- The budget file on `main` matches `token-measure.py` run on the latest release tag.
